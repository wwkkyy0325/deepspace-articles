——薄界面、厚能力：agent 原生软件的设计与收束

版本：2026-10 · 体裁：架构演化 + 设计哲学 + 可检索的工程记录 适合读者：agent 运行时 / AI Infra / 后端架构 / 产品技术负责人

一句话结论

把用户面压到最薄，把能力面做厚。 用户只表达意图、只看见状态；agent 直接调用结构化能力，不为“看懂界面”付出额外代价。本文记录一个运行时按这条原则演化、收束的全过程。

快速导读

如果你只有 3 分钟（非本领域读者）

  • 传统软件：功能 = 按钮。用户要学习界面，记住路径，理解术语。
  • agent 原生软件：功能 = 接口。用户只说目标；界面只负责“表达意图”和“看见状态”。
  • 难点不在接模型，而在三件事：状态别乱、上下文别炸、答案别假。
  • 本文讲的是：一个系统怎么把这三件事变成机制，而不是变成用户的设置项。

一个类比：餐厅。顾客只看菜单（薄界面）；后厨有一整套标准化流程（厚能力）。好的设计不是把后厨开放给顾客，也不是让顾客自己炒菜，而是让“点单”足够简单、“出餐”足够可靠。agent 时代的软件，就是把“后厨”做成 agent 能直接调用的接口，而不是让它透过窗口猜厨师在干什么。

如果你只记住三句话

  2. 深层接口是给 agent 的，不是给用户的；它必须结构化、语义化、零额外代价。
  3. 一致性先于功能；没有单一事实源，功能越多越乱。

本文的组织约定

第 5 节的每个设计都按同一结构书写：问题 → 决策 → 机制 → 代价 → 验证。这样人可以从任意一节读起，机器也可以按字段抽取、复用。附录 B 是面向检索的索引与可复用清单。

摘要

通用 agent 运行时的工程难点不在单次模型调用，而在长时间运行中的三件事：状态在实时视图、刷新与重连之间保持一致；上下文成本随会话增长而失控；模型输出必须被当作不可信输入来对账。本文介绍一个单人完成的通用 agent 运行时的架构与演进，并把它背后的设计哲学概括为「薄界面、厚能力」：人类面只保留意图表达与状态可见，能力面以结构化接口暴露给 agent，且不要求 agent 为“使用软件”付出额外代价；思考层放在云端，设备侧只保留必要的本地能力。

系统经历能力展开、一致性危机、系统收束三个阶段。最终形态把验证从“提交门”搬到工具边界，把上下文压缩从用户按钮变成五层自动梯子，把两套流式协议收敛为一套类型化事件契约，并把 agent 层级收敛为默认一级、最多两级。本文重点讨论三类特大重构（后端、中间层、前端）的判据与做法，以及由真实事故驱动出的可靠性机制。

关键词：agent 运行时；薄界面厚能力；事件溯源；上下文工程；可信输出；重构方法

1. 引言：软件的第一使用者正在变化

1.1 一个判断

过去，软件的第一使用者是人：人通过界面完成操作，API 是给开发者集成用的附属品。

现在正在发生的变化是：软件的第一使用者逐渐变成 agent。人不再逐步操作软件，而是表达目标；agent 理解目标、选择能力、执行、汇报。界面从“操作面板”退化为两件事：

  • 意图入口：让人把目标说清楚；
  • 状态出口：让人知道现在发生了什么、要不要介入。

这不是“在软件里加一个聊天框”。聊天框只是表面；真正要改的是能力如何被暴露。

1.2 薄界面、厚能力

由此得到一条设计原则：

表层给人，越薄越好；深层给 agent，越厚越好。

  • 薄界面：人类只需要表达意图、看见状态、做必要确认。每多一个设置项、每多一步向导，都是设计债。
  • 厚能力：每个能力都应该有名字、参数结构、返回结构、错误码、权限位、审计记录，能被组合、能被取消、能被重放。

关键约束是：深层接口不能让 agent 付出额外代价。

具体来说：

  • 不能让 agent 看截图、猜坐标——那是把人类界面反解析成机器接口，成本高、脆弱、且随界面变化而失效；
  • 不能让 agent 拼 shell 字符串——自然语言进 shell 既是安全问题，也是解析负担；
  • 不能让 agent 解析人类文案来推断状态——状态必须是结构化的数据，不是“界面上写着运行中”。

一句话：界面是给人看的，接口是给 agent 用的；两者可以共享同一套能力，但不能让 agent 走人的通道。

1.3 三条设计推论

从这条原则可以推出三条可执行的约束：

编号 推论 含义
P1 用户不管理系统 压缩、思考强度、恢复、验证都应自动；设置项是机制缺失的补丁
P2 能力以接口暴露 每个能力有 schema、错误码、权限位、审计；不以“按钮位置”表达
P3 系统承担验证与恢复 用户不该判断“它做对了吗”；系统给出证据、可回滚修正

P1 最容易被低估。它意味着每次讨论“要不要加个开关”，默认答案是否定的；只有当机制无法覆盖时才允许出现旋钮，而且旋钮必须能被自动路径取代。

1.4 一个提醒：14B 以下不要放在 agent 的思考层

这一条是踩过坑之后的结论，不是模型鄙视链。

以我们的经验，14B 以下的本地模型不能拿来当 agent 的思考层。 它在单轮问答上可能像模像样，但一旦进入多步工具调用，问题会成倍放大：

  • 工具名和参数格式错误率上升；
  • 计划保持不住，做着做着跑偏；
  • 长上下文里关键约束被忘掉；
  • 一次错误调用会引出更长的重试链，最后比直接调云端贵得多。

14B 是“能跑”的下限，不是“能长期跑”的推荐值。把这条写下来，是为了让后来的人少走一遍弯路：先别在本地小模型上雕 agent 的思考层，先把流程和工具链跑通。

本地和云端不是同一类工具。 本地模型在速度、有效上下文、工具调用可靠性、长任务稳定性上都有明显差距；云端的单次价格还在下降、质量还在上升。把本地 7B/14B 和云端主力模型放在一起比“性价比”，通常只比了显存和电费，没算上失败重试、调试时间、上下文长度和用户体验。

本地仍然有价值，但位置不同：

位置 适合本地 原因
语音识别 是 隐私、离线、延迟敏感；SenseVoice 随包分发
嵌入 / 分类 / 预处理 可选 窄任务、可离线；向量召回默认关闭
agent 的思考层 否（14B 以下） 多步规划与工具调用会被错误放大
长任务主力 否 有效上下文、稳定性、成本都不占优

这不是“本地永无机会”，而是：在 agent 的思考层这个位置上，本地小模型现在还不是一个划算的选择。 云端模型价格越来越低、质量越来越高，这个判断只会更强。

1.5 一个反例：把 UI 自动化当 agent 接口

“让 agent 看屏幕、点按钮”看起来很通用，实际上是让 agent 走人的通道：

  • 分辨率、动画、遮挡、延迟、主题变化，都会变成 agent 的维护成本；
  • 每一步都要视觉识别，token 与延迟远高于一次结构化调用；
  • 界面是给人优化的，不是给机器解析的，语义信息在视觉层已经丢失。

正确方向是语义化入口：组件树、能力 API、结构化状态。界面只是能力的一种投影，不是能力本身。

这也解释了为什么“深层接口零额外代价”是硬约束，而不是优化项：如果 agent 每次使用软件都要先“看懂界面”，那它就没有真正获得能力。

2. 问题：agent 原生软件的三类默认失败

一个能连续运行数小时的 agent，本质上是一个有状态的长事务服务。它同时面对三类失败：

  1. 一致性失败：流式视图、刷新后的历史、断线重连后的快照，三者对同一轮对话给出不同答案。
  2. 成本失败：上下文随轮次线性增长，直到模型窗口或账单先崩溃。
  3. 可信失败：模型声称做了某件事，但证据链并不存在；验证发生在草稿写完之后，只能整篇重答。

大多数 agent 项目在 demo 阶段绕开了这三类问题；一旦进入日常使用，它们会以“卡住”“刷新后答案没了”“答非所问”的形式集中爆发。本文讨论的正是一个系统如何从“能跑”走到“敢每天用”。

3. 系统总览

3.1 分层

kernel/    共享类型、上下文协议、遥测、会话模型
infra/     数据库、沙箱、网络、MCP、知识、向量、更新、能力探针
app/       agent 循环、服务端、工作流、A2A、IM、调度中心
adapters/  第一方平台适配器（注册进适配器表）
tools/     独立的搜索/浏览/打包工具

依赖方向严格单向：kernel ← infra ← app ← adapters/tools。服务端只做组装，不允许反向依赖；后期专门修过一轮“编排层反向依赖路由层”的倒挂，把卡生命周期、会话设置、发现配置下沉回编排层。

3.2 三个数据面

面 单一入口 职责
事件面 会话总线（单调序号 + 环形缓冲 + 增量 fold） 运行状态、UI 渲染、重连快照的唯一真相
上下文面 单一装配入口 + 阶段流水线 所有上下文只从这里进入模型
能力面 工具注册表 + 贡献注册表 工具、技能、工作流、MCP、通道统一接入

单一事实源不是口号，而是可检查的结构约束：同一份状态不允许出现第二个写入口；两套实现（Rust 服务端与 TypeScript 前端）必须共用同一套折叠规则，并用同一组 fixture 断言。

3.3 主链路

前端（编译进服务端二进制）
  → HTTP/SSE
  → 服务端 flow（命令分发 / 上下文装配 / 事件泵 / 收尾）
  → agent 循环（observe → solve → act → converge → close）
  → 工具 / 沙箱 / 子代理池

移动端不在主链路中，只是把同一个核心宿主进系统级应用——是宿主形态，不是架构分叉。

4. 演进：三次收束

4.1 第一段：能力展开（第 1–2 周）

从零建立 workspace，先落数据模型与 trait 边界，再实现 ReAct 循环、权限代理、沙箱、记忆与上下文阶段。这一阶段的策略是先展开：把能想到的能力面都铺出来，允许重复与粗糙。

事后看，这一步最重要的产出不是功能，而是边界：工具 trait、上下文阶段 trait、事件契约、数据库接口。边界一旦稳定，后续所有重构都有落脚点。

4.2 第二段：产品化与一致性危机（第 3–6 周）

系统开始被真实使用后，问题从“功能缺失”转向“状态不一致”。典型症状：

  • 流式期间看到的内容，刷新后消失；
  • 同一轮的工具卡片在实时视图和历史视图里数量不同；
  • 断线重连后，终态事件丢失或重复。

根因是同时存在两套流式协议和两套折叠实现。引入第二套协议时的理由是“字节兼容”，但代价是此后每次修复都要在两条链路上各做一遍，且两边行为逐渐分叉。

这一阶段最值得记录的不是修了多少 bug，而是承认双协议是错误决策，并规划一次彻底替换。

4.3 第三段：系统收束（第 7–13 周）

收束以“单一事实源”为原则，分四步：

  1. 删协议：两套流式协议收敛为一套类型化事件契约，旧帧格式在一个发布窗内双解析后删除。
  2. 删能力面：角色/人格栈、跨机 UI 中继、插件舰队、手动压缩按钮、零消费路由与幽灵阶段集中退役。
  3. 重构骨架：两千行的流程函数拆成生命周期段；八十个扁平状态字段按域收敛。
  4. 换前端：旧前端冻结为黄金母本，新前端分批追平后接管出货。

转折点的判据很朴素：一致性类缺陷是否断崖式下降。删除第二套协议后，这类缺陷从“每天都有”降到“偶发且可定位”。

4.4 决策与反转

决策 当时的理由 事后判定
引入第二套流协议并保留旧编码器 字节兼容、渐进迁移 反例：双份实现导致重复修复与行为分叉
删除第二套协议，建立总线 + 序号 + 权威视图 单一事实源 全局转折点
手动压缩按钮退役 五层自动梯子已覆盖 正确：减少用户心智负担
跨机 UI 中继退役，协议只承载通信 职责单一 正确：减少跨机状态耦合
手机端改为系统级宿主 权限与能力上限 正确：把运行时与形态解耦
深层能力以接口暴露，不以 UI 自动化暴露 agent 零额外代价 本项目的长期主线

5. 关键设计

每节按 问题 → 决策 → 机制 → 代价 → 验证 组织。

5.1 可靠性：以总线作为存活信号

问题：一次真实故障中，数据库工作线程被慢查询拖住；运行已经结束，但终态事件写不进数据库，客户端永远停在“运行中”。

决策：不要给数据库加超时了事，而是换一个在数据库阻塞时仍然可用的存活信号——会话总线。看门狗负责检测，不自动 kill；是否恢复由人决定。

机制：

  • 总线记录最后一次发布事件的时刻；看门狗每 30 秒扫描，静默超过阈值（默认 900 秒）的运行被取消并收到错误事件；
  • 停在等待用户输入/确认的运行被跳过，避免误杀；
  • 取消信号同时到达模型提供方、沙箱与进程树；
  • 命令退出后若后台子进程仍持有输出管道，等待 2 秒后放弃排空，用已收集输出返回；
  • 人工输入停放有 24 小时上限，到期持久化系统说明并收敛为断开；
  • 提供方连续失败 5 次后熔断 30 秒，避免拖垮进程。

代价：策略是“检测 + 人工恢复”，不是全自动；看门狗无法中断一条已经卡住的 SQLite 语句（该层没有逐语句超时），只能保证系统知道它卡住了。

验证：单元测试覆盖“静默运行被取消并收到错误事件”和“停在 ask_user 的运行不被误杀”；真实事故复现后复查健康端点和调试日志。

5.2 上下文：统一入口、分阶段预算、五层压缩

问题：上下文随轮次线性增长；此前把“压缩”做成按钮，等于把系统该做的判断转嫁给用户。

决策：所有上下文收口到单一装配入口；压缩做成五层自动梯子；每个阶段暴露可观测快照，让“上下文为什么长这样”可被逐项裁剪。

机制：

  • 17 个阶段（按 build_full_pipeline 的实际注册计数：默认 7 + 追加 10），按稳定优先级排序，每个阶段有独立 token 预算；
  • 压缩触发：任务完成优先——TodoWrite 列表转为全部完成时，立即做一次后台滚动压缩，把已完成任务的回合滚进持久摘要，不等窗口阈值；模型也可以主动调用 roll_summary；窗口 85%/90% 的阶梯是兜底；
  • 历史窗口不再用固定条数，而由 token 预算驱动；摘要水位线避免“摘要行 + 原始行”重复注入；
  • 每个阶段输出快照：名称、描述、消息数、估算 token、是否贡献；零贡献阶段在 UI 中置灰但不隐藏，装配顺序完整保留。

这套窗口阈值最早在 GAIA 期对齐 DeepSeek Harness：自动压缩 80%、观测掩码 70%、保留 16% 的尾部；后来校准到 85/85/90。它们只是兜底，第一触发点是任务边界。数字变了，三个原则没变：按窗口百分比、跟随模型窗口、压缩不破坏前缀缓存。

组装顺序：不是排版，是信息优先级

17 个阶段大致分四类：

类别 典型阶段 位置
约束 系统提示、工具定义、用户规则、回答纪律、验证要求 最前，稳定前缀
状态 任务状态、工作区、计划、todo 约束之后、检索之前
知识 技能、记忆（RRF）、领域知识、研究项目 中段，按预算与相关性
观察 工具结果、检索结果、实时用量 最后，最易变

顺序不是按类别平铺，而是按信息优先级解决四件事：

  1. 稳定前缀优先：系统提示、工具定义、用户规则放在最前；它们跨轮不变，prompt cache 才能命中。把易变内容混进前缀，会让缓存整段失效。
  2. 约束先于知识：规则、回答纪律、验证要求放在技能与记忆之前（或至少不晚于它们）；否则模型先读到“能做什么”，再读到“不许做什么”，约束会被稀释。
  3. 任务状态先于检索：当前任务、工作区、计划先于记忆与研究资料；模型先知道“我在做什么”，才知道“该回忆什么”。
  4. 验证靠近提交：问题建模、候选验证、提交对账放在最终答案之前；工具观察和检索结果靠后，因为它们最易变。

落到工程上，新增阶段不是 push 到末尾，而是声明优先级并接受稳定排序；每个阶段必须能回答：它解决哪一类冲突、为什么必须在这个位置。

这套顺序是在 GAIA 那一轮用简单对照定下来的：同一组题，换阶段顺序，看失败模式。稳定前缀 + 约束前置 + 状态先于检索 + 验证靠近提交，四条的收益是叠加的；反过来，把记忆或工具观察提到规则前面，最先坏的是“答非所问”和“约束漂移”。它不需要复杂消融就能看出来，所以后来没有再动。

单轮预算：宁可多轮，不要一轮跑很长

这里的“轮”指一次模型调用、一次上下文装配，不是一次用户请求；一个用户请求可以跑很多轮。这样做不是为了让上下文变小，而是为了把状态从上下文里搬到上下文外：

  1. 成本：每次调用都会重发当前上下文；一轮越长，后续每次调用越贵。多轮 + 稳定前缀缓存，边际成本更低。
  2. 质量：长上下文会出现中间遗忘和注意力稀释，关键约束、证据容易被淹没。多轮把中间结果写进 todo、文件、证据账本、记忆，下一轮只装配工作集，信号更干净。
  3. 可恢复：一轮跑很长，中途失败或取消就全丢；多轮天然有检查点，每轮可验证、可提交、可回滚。
  4. 可干预：轮与轮之间可以 steer、确认、停止；一轮到底没有介入点。
  5. 可观测：每轮有明确的输入、输出、终态，定位问题不靠猜。

轮数是结果，不是目标：预算约束的是每轮装多少，不是强行切轮；任务需要多少轮就跑多少轮。

所以预算不是“省 token”的口号，而是一个强制外化机制：上下文放不下的东西，必须变成文件、todo、证据或记忆；下一轮再从这些持久状态重新装配。压缩只是兜底，外化才是主路径。

压缩：任务完成即压缩，窗口阈值兜底

压缩的第一触发点不是窗口百分比，而是任务边界：

  • 任务完成（首选）：模型把 TodoWrite 列表推进到“全部完成”的那一轮，运行时立即起一次后台维护，把这一波已完成任务的回合滚进持久摘要，并推进水位线；只在 pending→done 的那一次触发，in_flight 防止重叠，当前 run 的尾部由后续 pass 接上；不等用量阈值——大窗口模型可能永远到不了 90%。
  • 模型主动：模型可以在任意回合调用 roll_summary，给出一段摘要和要保留的最近回合数（1–8，默认 2，摘要上限 4096 字符）；循环在下一个回合边界应用，当前工作尾部保持原文。
  • 窗口阈值（兜底）：85% 后台滚动 / 观测掩码，90% 自动压缩悬崖；用于没有干净任务边界、或没有 todo 列表的长跑。

任务边界优先的原因：任务完成时，结果已确定，过程可以安全地压成摘要；下一波任务从干净的工作集开始；水位线保持低位，90% 悬崖很少真正触发。

触发之后，具体分五层做，按成本从低到高：

层 做法 成本 触发
1 Snip 删空输出、ok/null 占位、取消结果；不删沙箱拒绝 0 每轮
2 ObsMask 最近 5 条工具结果保留全文，其余压成头 0 窗口 85%
3 Truncate 单个工具输出头 + 尾截断 0 每次工具输出
4 AutoCompact 用 LLM 摘要最老的消息 一次 LLM 调用 窗口 90%
5 Trim 硬删最老消息 0 摘要失败兜底

顺序的原则是：最便宜的先做，最贵的 LLM 摘要留到最后。 ObsMask 之所以要等到 85%，是因为它会改写对话中段，从改写点之后的前缀缓存全部失效；85% 以下保留完整工具结果（缓存命中后很便宜），85% 以上才在压缩悬崖前剪掉旧结果。

几个“以前不划算、现在值得做”的设计：

  1. 摘要追加，而不是折叠。 旧摘要消息保持逐字节不变，新摘要作为独立消息追加在后面；[system + 旧摘要] 前缀在多次压缩之间持续命中缓存，只有新追加的摘要付全价。折叠会改写旧摘要的字节，每次压缩都把缓存打掉。
  2. 结构化摘要，按耐久度分区。 摘要不是一段散文，而是 GOALS / CONSTRAINTS / FACTS / DONE / OPEN / NEXT 六段：前四段由系统按并集合并、不再喂回模型；只有 OPEN 会重新喂给模型，让它输出 RESOLVED 行；NEXT 保留当前活跃的尾部。FACTS 要求逐字节精确——路径、数字、URL、commit sha 不许改写、四舍五入或缩写。这样摘要不会在“摘要的摘要”里逐轮漂移。
  3. 模型自己决定何时滚。 模型可以调用 roll_summary，在它认为任务告一段落时主动请求滚动；循环在带内直接应用，不额外起后台 LLM 调用。后台滚动则是增量的：读持久摘要 + 水位线，只取水位线之后的消息，合并后推进水位线。
  4. 预算用真实 token 校准。 chars/token 比率用 provider 返回的真实 input_tokens 做 EMA 校准（CJK 文本不会按英文 4 字符/token 低估一倍）；校准前用 CJK 感知的估算器，保证压缩和预算用同一把尺子。
  5. 小模型也能压缩。 压缩模型窗口小的时候，消息按 窗口 - 1536 分块逐块摘要；模型不可用时退化为确定性抽取（头 + 尾 + 高价值行，标记 [extractive]），不阻塞主循环。

因为模型变强，删掉了几条“弱模型时代”的保守约束：

旧约束 现在 原因
只在窗口阈值压缩 任务完成即压缩 + 模型主动滚 + 窗口兜底 大窗口模型可能永远到不了 90%，任务边界才是自然压缩点
早期 65% 滚动摘要 85% 过早摘要会隐藏仍然有用的工作历史
早期 70% 观测掩码 85% 保留更多原始工具结果，模型扛得住
固定保留 4 条消息 保留 16% token 尾部 按预算而不是条数
128k 绝对滚动上限 取消，只留操作员环境变量 1M 窗口下 128k 只有 13%，模型还空着就开始藏历史
手动压缩按钮 删除 自动梯子完备，用户不该管理系统
压缩必须折叠进摘要 追加式摘要 保持前缀缓存

最后一条是稳定性：压缩是视图，不是删除。 压缩只从 messages 投影里删行，原始消息仍在 session_events 追加日志里；历史分页可以越过压缩地板继续回溯，第一个问题仍然找得到。这也是为什么用户不需要参与压缩——压缩不会让历史消失，只是让模型当前看到的工作集变小。

代价：阈值是经验值，需要持续校准；轮次多会带来编排开销和额外延迟，预算太小会频繁中断、太大又退化成“一轮跑很长”；任务边界压缩按任务完成触发，任务切得太碎会带来额外的摘要调用，todo 的粒度就是压缩的粒度；过度压缩会丢细节，因此必须保留可回溯的历史分页；阶段快照本身也有维护成本。

验证：固定任务集 + 真实会话做逐阶段回归，逐项判断“这个阶段是否改变了结果”；删除或合并前先证明效果等价；任务完成触发的边界压缩有单测（TodoWrite 全完成 → 后台摘要落库）；快照保证删完之后仍能解释上下文构成。

5.3 可信输出：从门控到内生

问题：早期在草稿写完后跑一组提交门，不通过就整篇重答。成本高、破坏已经流出的内容，且重提示是泛化的。

决策：把验证左移到动作边界；运行后只做锚点编辑，不做整篇重写。

机制：

  1. 动作时记账：检索类工具的结果进入证据账本，论断以 [E#] 绑定；
  2. 提交时对账：只检查覆盖率，缺哪补哪；
  3. 运行后修正：独立复核以锚点编辑修改正文——唯一匹配、删除预算有上限、最多 8 处、必须带来源、代码围栏平衡；任何一条不满足，整批降级为失败且原文不动。

代价：能绑定证据的论断才可修正；结论级正确性仍需要独立重算；锚点编辑偏保守，宁可少改也不误改。

验证：门控与后校验的单测；前端逐行 diff；真实运行 smoke；被拒绝的批次必须保持原文不变。

5.4 并发：三类并行，各自的闸门

问题：N 次检索串行执行，延迟是 Σ(latency)；但无脑并行会在依赖任务上劣化结果。

决策：按场景分三类，各自设边界，不做全局 join_all。

机制：

场景 并行条件 约束
同轮工具调用 只读白名单（搜索、读文件、代码检索） N 次调用从 Σ(latency) 降到 max(latency)
子代理扇出 子任务可分解为独立部分 上限 6 个；并行成本不超过剩余墙钟一半
后台任务 与主循环无状态依赖 独立注册表、可取消、结果持久化

子任务如果是顺序依赖的，明确禁止扇出。相位机（侦察 → 深挖 → 验证 → 提交）按剩余预算推进，保证并行不会挤掉综合与收尾的时间。

代价：只读白名单需要维护；扇出窗口被限制在深挖阶段；需要为综合保留时间预算。

验证：依赖型任务不扇出的用例；并行延迟行为；子代理结果持久化与取消路径。

5.5 层级：默认一级，最多两级

问题：多 agent 看起来像“更强的并行”，但每加一层，就多一次上下文重建、一次结果转述和一条终态路径。

决策：默认一级；只有当任务能拆成独立子问题、且子结果能在本轮被综合时，才开两级；不做三级。

机制：

  • 一级：主循环直接持有任务、工具、记忆与终态；工具调用就是能力调用，不做“主管→执行者”的转述。
  • 两级：父 agent 只做分解与综合；子 agent 拿到受控上下文（父工作区、工具白名单、权限继承、≤400 字的 T1 记忆、编排指令），完整父历史不回传；结果持久化，父会话通过唤醒或 steer 接回。
  • 扇出有闸门：子任务必须被声明为独立（SUBTASKS: n）；并行成本不超过剩余墙钟的 50%；最多 6 个 worker。
  • 等待分两种：只有验证/对照这类“本轮综合必需”的结果才前台等待（有界超时），其余后台完成后再唤醒父会话。
  • 三级不做：中间层没有自己的信息面，只会变成消息路由器；每传一层，证据、约束与权限都会衰减，终态、取消与审计归属也会变模糊。

GAIA 期把这个判断固化成 ADR 0009：Supervisor / SubAgent / Verifier 是软角色标注，不是硬切三层。系统实际只有两级执行层，Verifier 是角色而不是第三层；硬结构层级被明确列为不做。

什么时候需要两级：

  1. 问题能拆成 2–6 个互不依赖的子问题（并行研究、独立验证、多来源对照）；
  2. 子任务需要隔离（不同工作区、不同工具集、不同权限）；
  3. 子结果可以被验证并综合，而不是把原文丢回父上下文。

为什么一级通常最好：

  • 上下文只需要组装一次；子 agent 要重新建立任务、工具与约束；
  • 父子之间是有损通道：子 agent 的完整推理无法无损回传，父 agent 只能看到摘要；
  • 终态和取消只有一条路径；多一层就多一种“谁先结束”的竞态；
  • 大多数任务是顺序依赖的，并行只会增加协调成本。

代价：一级在真正可并行的研究任务上慢；两级需要额外的上下文隔离、结果格式与唤醒机制。

验证：GAIA 那一轮做的是简单验证——换层级、换组装顺序，观察失败模式，而不是刷分。GAIA 的 Level-1 题大多是单线程检索与计算，独立子问题少，所以一级通常够用；两级只在多源对照、并行检索这类真正可分解的任务上才有收益。结论不是“多 agent 一定差”，而是：在没有独立子问题和可验证综合点的任务上，加层只会增加失败面——三级带来的不是能力，而是重复检索、证据转述失真和终态竞态。 后来扇出闸门的三道条件（可分解性、成本、上限 6），就是这条结论的工程化。逐题失败分类见 8.3。

5.6 自适应思考强度

问题：把思考强度做成用户旋钮，用户既不知道该调多少，也不该为一次对话的学习成本买单。

决策：做成一条单向阶梯：每个运行从低档开始，遇到难度信号、连续失败或验证未过时升级，运行结束重置。

机制：进程级共享的原子档位；升级单向；运行开始复位。刻意不做按运行隔离——它是每次调用的推理深度提示，不是正确性状态；并发运行读到升级值只会多花少量思考 token，不影响结果。

代价：并发运行共享一个提示值；极端情况下一个难任务会让同时进行的简单任务多花一点思考成本。

验证：升级触发点的单测；简单/困难任务的 token 与耗时对比；正确性不受并发影响的回归。

5.7 终态：单一出口

问题：长事务服务最容易出错的是结束路径：多个 return/continue 分支、终态事件重复或丢失、重连流在异步校验结果到达前就关闭。

决策：把循环拆成五段，每段用哨兵类型把 continue/return 映射成显式状态，保证只有一条终态路径；重连退出条件改为注册表为空。

机制：

  • observe → solve → act → converge → close 五段；
  • 收敛段与收尾段各有一个哨兵枚举，所有分支映射过去；
  • 终态事件恰好一次；
  • 重连流只在 运行中 ∪ 后台任务 ∪ 事后校验 三个注册表同时为空时关闭。

代价：引入显式状态类型，重构成本更高；哨兵枚举必须与循环语义严格对应，否则会出现“看起来收敛了但漏了分支”。

验证：折叠 fixture 双侧断言；静默运行/停放运行/后台任务/事后校验的退出条件单测；重连场景的真实 smoke。

5.8 面向 agent 的接口设计

问题：如果 agent 只能通过人类界面使用软件，它就要为“看懂界面”付出额外代价：视觉解析、坐标猜测、文案理解、状态推断。这既慢又脆，而且与界面变化强耦合。

决策：把软件能力做成结构化接口，界面只是能力的一种投影。人类面只保留意图与状态；agent 面暴露完整能力。

机制：

  • 能力有名字和 schema：参数结构化、返回值结构化、错误码显式，不靠自然语言约定；
  • 状态是数据：运行中、等待确认、失败、完成都是类型化状态，不是界面文案；
  • 权限是一等层：能力调用先经权限代理，高危动作进入特权服务并留审计；确认只针对真正高风险的动作；
  • 可取消、可重放、可审计：每个长动作都有取消路径和终态；每次调用有记录；
  • 语义优先于视觉：能用能力 API 就不点界面；需要兜底时用语义树，而不是截图坐标；
  • 深层接口不是复杂度：一个功能可以有一个人类入口和 N 个 agent 入口，这是能力面的厚度，不是产品臃肿。判断标准是“agent 调用它是否需要额外代价”。

代价：接口设计要前置，版本与兼容要管理；权限面变大，需要更严格的审计与默认拒绝；旧软件没有能力接口时只能走语义兜底。

验证：每个能力必须能在不打开界面的情况下被调用；拒绝路径与审计记录可查；高危动作必须有确认与回滚。

5.9 记忆：上下文之外的第二层状态

问题：上下文是工作集，不是仓库。把所有历史都塞进上下文，成本高、信号差；把历史全丢掉，又会重复犯错。

决策：把长期状态放到上下文之外，用“日记 → 主题 → 事实”三段式沉淀；上下文只按需召回。

机制：

  • LIGHT（轻）：定时/提醒触发，把原始对话裁剪后追加到日记（diary/YYYY-MM-DD.md），只追加不覆盖，不写长期记忆；
  • REM（主题）：按天从日记抽取主题，写入 themes.jsonl，仍然不写长期记忆；
  • DEEP（事实）：对主题做六维打分（相关性、频率、查询多样性、新近度、整合度、概念丰富度），过阈值后做 ADD / UPDATE / DELETE / NOOP 合并，再写 facts/*.md + SQLite FTS5 + 图；
  • 召回：RRF 排序注入；向量召回是可选路径且默认关闭，关闭时走关键词；子代理只注入 ≤400 字的 T1 记忆，不复制父历史。

晋升为什么严格，而不是宽松

记忆的错误是不对称的：漏掉一次召回，只损失一次检索；错误晋升一条全局事实，会污染之后所有会话。旧设计正好踩了这个坑——主题在创建时就被打上 global，DEEP 的门用 passes_gates(1, 1) 而召回门槛是 2，等于只看置信度；结果是某个测试会话的临时结论变成了永久全局记忆，之后每个相关会话都能召回它。

现在的规则是四道闸：

闸 规则 防的是什么
出生范围 新主题/事实只落会话工作记忆，创建时绝不写 global 一次会话的临时结论直接变成全局
晋升条件 在出生会话里被真实召回 ≥3 次，才毕业到全局/T1 单次 LLM 置信度、单次模式匹配导致的误晋升
不做 LLM 标注 不用 LLM 给主题打“来源会话/类型”标签 标注本身会幻觉，等于再加一层会漂移的信任链
删除语义 删会话时，会话级事实随之清除；全局事实作为“泛化结论”保留，由陈旧清扫、满仓归档和手删兜底 会话删除后仍残留、或全局池无限膨胀

检索侧也收口：一个会话只能看到“自己的会话事实 + 全局事实”，毕业前不会跨会话注入。

为什么宁可严格：记忆污染是信任问题，不是召回率问题。少召回一条，用户最多再问一次；错晋升一条，之后每个会话都可能被它带偏。冷启动慢一点，比“所有会话都被一条脏事实污染”便宜得多。

代价：三段式有延迟，事实不是“聊完立刻全局可见”；毕业需要三次真实召回，冷启动会慢；向量关闭时召回质量依赖关键词。

验证：合并动作的单测（ADD/UPDATE/DELETE/NOOP）；三次召回毕业、陈旧清扫、跨会话不泄漏；记忆审计与导出。

6. 特大重构的方法学

6.1 后端：行为保持 + 逐提交绿 + 搬迁审计

两千行的流程函数拆成四个模块（命令分发、上下文装配、事件泵、收尾），两千行的循环拆成五段（干预、执行、收敛、收尾），八十个扁平状态字段按域收敛。

规则：

  • 只按扣除测试后的代码行判断是否拆分，不为行数均匀而拆；
  • 每个提交独立通过全量测试，任何一步都能单独回滚；
  • 纯搬迁用 --color-moved 逐段审计，证明“只是移动”；
  • 控制流改造用哨兵枚举，而不是在外面包一层 if。

6.2 中间层：契约先行，迁移在后，删旧最后

中间层最容易“改一半”。固定顺序是：

  1. 测绘：盘清两套协议、两套折叠、两套适配器的真实调用面；
  2. 契约先行：定义单一类型化事件，补跨语言 fixture；
  3. 双端同构：服务端与前端实现同一套折叠规则，fixture 被两侧同时断言；
  4. 删旧路：旧 shim 与旧帧格式在一个发布窗内双解析，确认无调用方后整段删除。

6.3 前端：黄金母本 + 分批对齐 + 零后端改动

旧前端冻结为黄金母本，只作对照与回滚基线；新前端按批次追平（会话骨架 → 对话体验 → 视觉体系），每批独立验证。视觉重做坚持“只换 token 与组件形态”，零服务端改动、零契约改动；已有变量名保留，避免组件类名连带重写。

6.4 共同规则

  1. 先测绘，再动刀；
  2. 每步可回滚；
  3. 行为保持要有机器判据（测试、fixture、搬迁审计）；
  4. 删除旧路径放在最后，并留一个发布窗；
  5. 文档同步，过期的描述要标注“描述漂移”，而不是假装没发生。

7. 可维护性是怎么被设计出来的

手段 做法 效果
单一入口 上下文、事件、扩展各只有一个入口 新增能力不需要改 N 个调用点
单一协议 两套流协议收敛为一套 消灭“两边各修一遍”的重复缺陷
契约即测试 fixture 被两种语言同时断言 跨语言漂移在 CI 被拦住
度量面 阶段快照、token 账本、环形日志、慢查询告警 问题可定位，不靠猜
删除机制 三份测绘（crate / 路由 / 特性）+ 逐项拍板 删得动，且不误删运维与 AI 调用面
质量门 fmt + 静态检查 + 全量测试 + 前端构建，工具链固定 重构不会悄悄破坏别处
文档系统 现状、任务步骤、变更理由分开记录 上下文能跨会话存活

一个值得单独说的判据：删除时“前端零调用”并不充分，还必须排除运维面与 AI 调用面。否则会把“当前没人点、但 agent 会调用”的能力误删。这与“薄界面、厚能力”是同一件事的两面：用户不点的接口，可能正是 agent 最需要的接口。

8.3 GAIA 期的失败分类

GAIA L1（53 题，官方 type-aware 评分）的内部基线是 27/53；逐题审计后，26 个失败分成 7 类：

失败类型 数量 典型表现
答案形态错误（算对了但没按评分器可读的形式提交） 11 值在正文里，但没有 Final answer:，或单位、逗号、解释混在一起
提交了错误答案 6 选错候选、读错约束、列表顺序错
检索死路 / 反爬 3 页面迁移、IP 拦截、空结果被当成失败
计算 / 工具超时 2 精确 DP 被 30s 子进程超时杀掉；长抓取超过墙钟
视觉 / OCR 缺口 2 纯文本模型没有图像路径
附件未注入沙箱 1 路径注入了，但沙箱没有只放附件
值已算出但从未提交 1 结论在推理里，最终答案没写

两个结论直接改变了设计：

  1. 答案形态是最大单一失败源（11/26）。把“算对”变成“以评分器可读的形式提交”，比再加一层推理更有效；这后来变成 AnswerDisciplineStage（priority 2）和最终答案契约。
  2. 只改抽取器没有用。对 26 个失败做“最后一句 / 任意标签 / 尾部片段”的机械抽取，只找回 0–2 个，还弄坏 3–4 个原本通过的题；真正的杠杆是模型侧提交纪律，不是 harness 猜答案。

后续修复把内部基线推到 L1 45/53、full-165 134/165。这些数字只作内部回归与失败模式，不作为对外成绩；逐题原始 JSON 已经丢失，失败分类是从当时的审计文档和 git 记录里恢复的。

8.4 事故驱动的验证

三起真实事故被完整记录为“现象 → 证据 → 根因 → 机制 → 验证”：

  1. 数据库工作线程阻塞导致终态丢失 → 总线看门狗 + 慢语句告警；
  2. 后台子进程持有管道导致运行挂死 → 排空宽限；
  3. 设备反复关机 → 从引导原因、电源管理日志与电池节点定位为框架温度断电，最终用只读文件系统覆盖 + 守护进程钳制。

这些修复的价值不在单个 bug，而在于它们都变成了常驻机制，后续同类问题不再复发。

8.5 效度威胁

必须诚实说明：

  • 这是单人开发、有限真实负载的系统，过程指标不能直接外推为团队效率；
  • 上下文逐阶段裁剪是观察性回归，不是随机对照实验；效果等价是工程判断，不是统计结论；
  • GAIA 期的逐题原始 JSON 已丢失（本机、备份与回收站中都找不到）；保留下来的只有脚本、30 题集、失败分类和内部聚合基线（L1 27/53 → 45/53，full-165 134/165）。这些数字只作内部回归，不对外引用——样本小、污染风险高。
  • 部分版本号在历史中缺失，说明发布流程并非完全严格。

9. 经验与反例

  1. 一致性先于功能。没有单一事实源之前，新增功能只会增加不一致的入口。
  2. 减法需要判据。“没人用”不是判据，“是否构成 agent 能力面”才是。
  3. 重构需要机器证明。全绿、fixture、搬迁审计，把“我以为没改坏”变成“证明没改坏”。
  4. 事故要沉淀为机制。修一个 bug 不算完成，去掉这类 bug 的生存条件才算。
  5. 界面越薄，接口越要厚。用户面少一个按钮，能力面就多一分结构化。
  6. 不要让 agent 走人的通道。截图、坐标、shell 拼接、文案解析，都是额外代价。
  7. 用户设置是机制欠债。每留一个旋钮，都要问：它能不能被自动路径取代？
  8. 反例同样有价值。双协议决策被完整记录并写进复盘，比假装一直正确更有用。
  9. 层级不是能力，是成本。默认一级；只有在独立子问题和可验证综合点同时成立时才开两级；三级只会增加失败面。
  10. 思考层放云端。14B 以下的本地模型不要把 agent 的思考层当试验田；省下的 API 费会在失败重试、调试和用户体验里还回去。
  11. 记忆宁可漏召回，不可错晋升。一条脏的全局事实会污染所有会话；召回失败只是多问一次。晋升严格，是对信任的保护。

10. 结论

通用 agent 运行时的成熟度，不取决于接入了多少工具，而取决于三件事是否被结构化地解决：状态是否只有一个真相、上下文是否可计量地裁剪、输出是否被当作不可信输入来对账。

而 agent 原生软件的成熟度，取决于另一件事：能力是否被做成了 agent 可以直接使用的接口，而不是必须透过人类界面才能触达的功能。

本文描述的演进路径可以概括为一句话：

先把能力展开到边界，再用单一事实源把它们收束成一个系统；表层给人，越薄越好；深层给 agent，越厚越好，且不让 agent 付额外代价。

收束的代价是持续的删除与重构；收益是系统开始变得可预测——而这正是“能每天用”和“能演示”之间的差别。

B.3 适用边界

本文的方法适用于：长时运行的 agent 服务、需要人类与 agent 共用同一套能力的软件、对状态一致性与可追溯性有要求的系统。

不完全适用于：一次性脚本、无状态问答、以模型训练/推理优化为核心的系统，以及没有权限边界的纯本地玩具项目。
